# 融合工作流 vs 纯 RAG：一次对照实验

27 条用例 · 2026-10 · 45 个商品的库

## 1. 一句话结论

短对话 26 条：**26 : 26 打平**。
加上一条 9 轮长对话：**融合 27/27，纯 RAG 26/27**。

更准确的读法：**长对话场景下纯 RAG 有结构性缺口**（历史窗口淘汰）。T7 重复 5 次：**纯 RAG 0/5、融合 5/5**。但曾观察到 1 次融合失败（router 把一句闲聊判成 product → 清空 `current`，见第 7 节）。

所以结论不是「融合更好」，而是：**融合的优势是有条件的** —— 只在长对话（或闲聊占比高）时才显现；短对话里它更贵（调用次数 2×）。

## 2. 问题

**纯 RAG 在什么条件下不够用？融合工作流能不能补上？**

不是问「融合好不好」，而是问「什么条件下需要它」。

## 3. 实验设计

**两套对照**

| | 纯 RAG | 融合工作流 |
|---|---|---|
| 检索 | 每轮无条件检索 | router 分流：product 检索 / chat 不检索 |
| 商品状态 | 无 | `current` 保存当前商品（供代词替换） |
| 历史 | 历轮**检索结果也写入历史** | 两层历史：检索结果用完即弃，不进历史 |

**基线故意做得强**：纯 RAG 也把检索结果写进历史。如果基线只存自然对话，T1–T4 的指代题它会直接输 —— 对比就成了「给对手放水」。**选强基线，是为了让「打平」这个结论站得住。**

**三个变量**：① router（意图分流 + `has_pronoun` 指代判断）② `current` 商品状态 ③ 两层历史

**测试集**：20 条单轮 + 7 条多轮 = 27 条。覆盖库内 / 库外 / 属性筛选 / 多对象 / 政策 / 闲聊 / 指代 / 污染 / 长对话。**每条期望值都先用检索器 probe 过实况再写** —— 期望值不是凭印象编的。

**扩库前提**：5 商品时 `HYBRID_TOP_N=5` 恰好等于库大小 → 每轮检索都返回全库（连「你好呀」都返回 5 个商品）→ 三个变量全被抹平。
扩到 45 SKU 后，检索才开始真正在筛。

**判据**：`must` / `must_not` 关键词判据。数字关键词卡边界（`299` 不会被 `1299` 命中）；命中 0 个或 >1 个完整型号名时，型号置顶规则不生效。

## 4. 结果

| | 短对话 26 条 | + 长对话 T7 | 调用次数 | 输入 token | 输出 token | 模型耗时 |
|---|---|---|---|---|---|---|
| 纯 RAG | 26/26 | **26/27** | 42 | 67,524 | 5,713 | 49.1s |
| 融合工作流 | 26/26 | **27/27** | 84（2×） | 63,046 | 7,992 | 74.9s |

**唯一的差异是 T7**（第 1 轮问耳机 → 7 轮闲聊 → 第 9 轮「它多少钱」）：

```
纯 RAG ✗  "你说的是哪一款呀？上面列了好几款商品，我这边看不到你具体指哪个～"
融合   ✓  "您问的是 AirPro 无线降噪耳机吧～它的价格是299元"
```

**成本会随对话变长而反转**：

- 短对话：融合更贵（每轮多一次 router 调用）
- 加上 T7 后：纯 RAG 的输入 token **反超**（67,524 vs 63,046）—— 它每轮把整段文档塞进历史，越聊越贵
- T7 单条重复 5 次的实测（同一条 9 轮对话，不含其他用例）：输入 token 纯 RAG **27,168–30,610（均值 28,407）** vs 融合 **12,557–13,307（均值 12,850）** → **2.2×**

## 5. 为什么短对话打平

**纯 RAG 的「历史全塞」是一个粗糙但有效的记忆。** 它把上一轮的完整检索结果留在历史里，所以指代题也能答对 —— 不是理解了指代，是碰巧上下文里还有。

三个变量的优势，需要三个条件才出现，而短对话 26 条一个都没满足：

| 条件 | 短对话里为什么没出现 |
|---|---|
| 库不够大 | 45 SKU，检索一次就够，`current` 没发挥空间 |
| 对话不够长 | 最长 3 轮，`history[-20:]` 装得下；纯 RAG 每轮 3 条 → 要超过 6.7 轮才开始淘汰 |
| 闲聊占比低 | 26 条里只有 2 条闲聊，省下的调用抵不过 router 的开销 |

**打平 ≠ 融合没用** —— 是触发条件没到。T7 把「对话不够长」这个条件补上之后，差异就出现了。

## 6. 净收益：对照过程修掉的两个真缺陷

**① 检索排序：长名字的兄弟款压过正主**

用户点名 `AirPro 无线降噪耳机` 时，`AirPro 2` 同时排到第 1：

- BM25：P006 描述里重复出现「AirPro」→ 词频更高（14.626 vs 13.967）
- 向量：兄弟款文本几乎同构，余弦 0.7943 vs 0.7850

模型因此答了 399（AirPro 2 的价）。

修法：**型号精确匹配置顶** —— query 归一化后包含某商品的完整 name，就把该商品挪到第 1；命中 0 或 >1 个不动；必须在 `[:TOP_N]` 截断前做。验收 12/12（含无空格 / 小写 / 全角归一化）。

**② router 类型静默失败**

在一次 40 条意图识别日志里观察到 3 次异常形态（`['product']`×2、`False`×1），另有 `None` 和整个对象 `{'route':...}` 的形态。这不是受控统计；修复后每次异常都会打 warning，但**尚未统计稳定发生率**。
而 `handle_turn` 用 `== "product"` 判断 → 这些全掉进闲聊分支 → **完全不检索** → 模型只能说「查不到」。整个过程不报错，只有日志能看见。

修法：小写归一 + 非法兜底 `product` + `logger.warning`（原始值必须打出来）；`has_pronoun` 必须返回真 bool（字符串 `"false"` 是 truthy），非法兜底 `False`（**宁可保留用户原话，不要误替换**）。单元测试 11/11。

兜底的方向是「**宁可多查一次，不能漏查**」：异常或格式不符 → 强制走检索，避免"用户在问商品、系统却没查库、模型凭空回答"。

**③ 顺带验证了 `current` 的长对话价值** —— T7 是唯一一条只有融合能过的用例。

## 7. 局限

1. **关键词判据是代理指标，不是事实本身。** 它分不清「列为答案」和「提到并排除」，实测误伤过 3 条（已修正）。残余风险在 T2/T3/T4（兄弟款的价格/规格值可能被"对比式表述"误伤）。
2. **重复 5 次的结果，以及一次反例。** T7 重复 5 次：纯 RAG **0/5**、融合 **5/5**，输入 token 也稳定（2.2×）。但曾观察到 1 次融合失败 —— `你叫什么名字` 被 router 误判成 product → 清空 `current`。**纯 RAG 的失败是结构性的**（3 条/轮 × 8 轮 = 24 > 20 窗口），**融合的通过依赖闲聊轮不被误判**（5 次样本里未复现，但确实发生过）。
3. **「两层历史」的价值没有被单独隔离测量。** 污染用例（T6）两套都通过。它目前是设计论证 + T7 的成本证据，不是独立的对照结果。
4. **`current` 多候选歧义未解决 —— 两套都会猜。** 「你们有耳机吗 → 它多少钱」重复 5 次：`current` 每次都存 5 个；**融合 0/5 反问、纯 RAG 0/5 反问**，两套都直接猜了一个（融合稳定猜 `ClearVoice 89元`，纯 RAG 稳定猜 `BassCore 199元`）。方案已定（`current` 置空 + 反问澄清），未写代码。
5. **未做的验证**：更大商品库；RAGAS 的 Faithfulness / AnswerCorrectness（需装包 + 写参考答案，当前判断是性价比不高）。
6. **测试集本身有选择偏差。** 每条期望值都是先 probe 检索实况再写的，可能不知不觉只保留了检索器能处理的题 → 可能**高估绝对准确率**；但两套用同一套题，**相对结论不受影响**。
7. **结论的适用边界。** 本次结论只覆盖「短对话 + 低闲聊占比 + 45 SKU」。要把它推广成一般结论，至少还需要：更长的对话样本、闲聊占比高的会话、明显更大的商品库，以及同一用例的多次重复。
